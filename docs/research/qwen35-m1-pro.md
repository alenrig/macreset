# Qwen3.5 on the 16 GiB M1 Pro for Pi

Researched 2026-10-24 for [the model/runtime research ticket](https://github.com/alenrig/macreset/issues/25). This is a primary-source design review, not an inference benchmark. The target Mac reports an M1 Pro and 16 GiB unified memory; no Qwen model was downloaded or run.

## Viable model sizes and formats

| Candidate | Published Q4 artifact | Trade-off |
| --- | --- | --- |
| `qwen3.5:9b-q4_K_M` | Ollama lists a 6.6 GB Q4_K_M language-model artifact, plus a 456M-parameter BF16 vision projector; its combined tag is 7.6 GB. | Stronger candidate for coding and tool use, but leaves less room for context, the server, and other Mac apps. |
| `qwen3.5:4b-q4_K_M` | Ollama lists a 3.3 GB Q4_K_M language-model artifact, plus a 334M-parameter BF16 vision projector; its combined tag is 4.0 GB. | More memory headroom and likely faster on this machine, at a clear loss in Qwen's own coding and function-call evaluations. |
| `qwen3.5:27b` or larger | Ollama lists the 27B family at 17–20 GB before inference overhead; 35B starts at 22 GB. | Exceeds this Mac's 16 GiB unified memory before useful context is allocated; exclude as a default. |

Artifact sizes and exact Ollama tags are from the runtime publisher's [9B Q4 listing](https://ollama.com/library/qwen3.5:9b-q4_K_M), [4B Q4 listing](https://ollama.com/library/qwen3.5:4b-q4_K_M), and [family listing](https://ollama.com/library/qwen3.5). Qwen's own [model cards](https://huggingface.co/Qwen/Qwen3.5-9B) describe the 9B and 4B base weights and native 262,144-token context. These Ollama artifacts are publisher quantizations of Qwen's models; they are not GGUF files published in Qwen's Hugging Face organization. The Ollama listing's model artifact size is a download/storage datum, **not** measured peak resident memory. [Qwen 4B card](https://huggingface.co/Qwen/Qwen3.5-4B); [Qwen 9B card](https://huggingface.co/Qwen/Qwen3.5-9B).

Qwen reports 9B versus 4B as 65.6 versus 55.8 on LiveCodeBench v6 and 66.1 versus 50.3 on BFCL-V4. These are Qwen's published evaluations of the original models, not measurements of the Q4 quantizations or Pi on this Mac. Both model cards document tool-use serving configurations. The gap makes 9B Q4 the first model to test for a coding agent, with 4B Q4 the memory fallback. [Qwen 9B results and tool configuration](https://huggingface.co/Qwen/Qwen3.5-9B); [Qwen 4B results and tool configuration](https://huggingface.co/Qwen/Qwen3.5-4B).

## Context memory and practical limit

Both Qwen cards specify 32 layers with eight full-attention layers, four KV heads, and 256 dimensions per KV head. **Derived estimate:** with two FP16 bytes per value and separate K/V arrays, the full-attention KV cache alone is `8 × 4 × 256 × 2 × 2 = 32,768` bytes per token: roughly 1 GiB at 32,768 tokens, 2 GiB at 65,536, and 4 GiB at 131,072. This omits recurrent state, vision components, graph/work buffers, process overhead, and macOS/apps; actual server allocations and KV-cache precision vary. The estimate follows from [Qwen's 9B architecture](https://huggingface.co/Qwen/Qwen3.5-9B) and [4B architecture](https://huggingface.co/Qwen/Qwen3.5-4B), which specify the same attention-head layout.

Qwen states 262,144 native context and advises at least 128K to preserve thinking capabilities, while warning that context may need to be reduced to avoid OOM. Pi's [llama.cpp guide](https://pi.dev/docs/latest/llama-cpp) starts with `-c 32768` and says omitting the limit can use substantially more memory. Ollama's [context guidance](https://docs.ollama.com/context-length) says coding/agent use should have at least 64K, that larger context consumes more memory, and that systems under 24 GiB default to only 4K. These recommendations conflict with the 16 GiB target; **a 32K or 64K starting limit is a pragmatic inference, not a validated quality target**. A 128K 9B setup could be tight once the estimated 4 GiB KV cache and runtime allocations are added. The final context value needs a live memory and Pi task check.

## Serving options

**Pi's native llama.cpp router:** Pi directly supports a current `llama-server` router over local GGUF files, `--jinja` for chat templates/tool calls, GPU offload, explicit context size, model load/unload, and connection through `LLAMA_BASE_URL`. Its [local-model guide](https://pi.dev/docs/latest/llama-cpp) is the closest Pi-native route. A Qwen3.5 GGUF must come from a selected third-party conversion or be converted from [Qwen's original weights](https://huggingface.co/Qwen/Qwen3.5-9B); verify provenance, exact file hash, and tool-call behavior before locking an automated download. Pi documents its own Hugging Face download picker but that is interactive; the Ansible role will need a non-interactive download strategy. [Pi local-model guide](https://pi.dev/docs/latest/llama-cpp); [Qwen original model card](https://huggingface.co/Qwen/Qwen3.5-9B).

**Ollama:** Its registry exposes explicit `qwen3.5:9b-q4_K_M` and `qwen3.5:4b-q4_K_M` tags and an OpenAI-compatible local endpoint. Pi documents configuring Ollama in `~/.pi/agent/models.json`, and Ollama documents the `ollama pull`/server path. This gives the Ansible role a named automatic model pull, while Pi uses the compatible endpoint instead of its llama.cpp router controls. The tag should be pinned by digest or otherwise checked to avoid an unreviewed quantization change on rerun. [Ollama Qwen tags](https://ollama.com/library/qwen3.5); [Pi compatible-endpoint guide](https://pi.dev/docs/latest/models); [Ollama API compatibility](https://docs.ollama.com/api/openai-compatibility).

**MLX:** Ollama also publishes 4B and 9B MLX variants; its [family listing](https://ollama.com/library/qwen3.5) gives 4.0 GB and 8.9 GB respectively. This is an Apple-oriented alternative, but this source review found no first-party Pi-specific advantage over llama.cpp's router or Ollama's documented endpoint. It merits benchmarking only if the default proves too slow. [Ollama Qwen family](https://ollama.com/library/qwen3.5); [Pi model connections](https://pi.dev/docs/latest/models).

## Research recommendation for the later decision

Start the decision with **9B Q4_K_M at an explicit 32K or 64K context**, because Qwen's original 9B is materially stronger than 4B on coding/function-call evaluations while its quantized artifact is below 16 GiB. Keep **4B Q4_K_M** as a documented fallback and expose model, quantization/digest, context size, and server runtime as role variables. Favor **Ollama for a first idempotent implementation** if the deciding factor is an exact named pull and simple Pi endpoint configuration; favor **Pi's llama.cpp router** if `/llama` model management and Pi-native integration matter more. This is an inference from the cited docs, not a measured 9B performance guarantee. [Qwen benchmarks](https://huggingface.co/Qwen/Qwen3.5-9B); [Ollama model listing](https://ollama.com/library/qwen3.5); [Pi local runtime guide](https://pi.dev/docs/latest/llama-cpp).

Before implementation fixes the default, run one 9B Q4 candidate on this exact Mac at 32K and 64K, issue a small multi-step Pi tool-call task, and record `ollama ps`/server memory, response speed, and errors. Ollama documents `ollama ps` for loaded/offloaded model status and warns that context allocation grows with length. [Ollama context guidance](https://docs.ollama.com/context-length).
